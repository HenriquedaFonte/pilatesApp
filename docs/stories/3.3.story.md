# Story 3.3 — Banco + Storage: Recibos, Numeração, Imutabilidade e Anulação

**Epic:** 3 — Recibos para Seguro Saúde (PRD-002)
**Status:** Concluída (migration e teste AC-8 rodados em produção em 2026-11-12)
**Estimativa:** M (4–6h)
**Tipo:** Database + RLS + Storage + RPC
**Esforço:** dev-critico
**Depende de:** Story 3.1

---

## User Story

**Como** professora,
**Quero** que cada recibo emitido fique registrado com número único, não possa ser alterado, e só possa ser anulado com motivo,
**Para que** eu tenha um histórico confiável para o seguro e para mim.

---

## Acceptance Criteria

- [x] **AC-1:** Tabela `insurance_receipts`:
  - `id UUID PK DEFAULT gen_random_uuid()`
  - `receipt_number TEXT UNIQUE NOT NULL` (ex.: `K-2026-0001`, `N-2026-0001`)
  - `receipt_type TEXT NOT NULL CHECK (receipt_type IN ('kinesitherapy','naturopathy'))`
  - `student_id UUID NOT NULL REFERENCES profiles(id)` (sem cascade — recibo é documento fiscal)
  - `issued_by UUID NOT NULL REFERENCES profiles(id)`, `issued_at TIMESTAMPTZ NOT NULL DEFAULT now()`
  - `snapshot JSONB NOT NULL` — todos os dados impressos (paciente, titular, apólice, praticante, licença)
  - `treatments JSONB NOT NULL` — `[{date, amount}]`, 1 a 10 itens
  - `products JSONB NOT NULL DEFAULT '[]'` — `[{name, price}]`, 0 a 4 itens, só naturopathy
  - `consultations_count INT`, `total_fees NUMERIC(10,2)`, `total_products NUMERIC(10,2)`
  - `pdf_path TEXT`
  - `status TEXT NOT NULL DEFAULT 'issued' CHECK (status IN ('issued','void'))`, `voided_at`, `voided_by`, `void_reason TEXT`
- [x] **AC-2:** RPC `issue_insurance_receipt(p_student_id, p_type, p_snapshot, p_treatments, p_products)` — `SECURITY DEFINER`, valida que o chamador é professora, valida quantidades (1–10 / 0–4, produtos só em naturopathy), calcula totais no servidor, gera `receipt_number` com sequência por tipo e ano (tabela `receipt_counters` com `SELECT ... FOR UPDATE`), insere e retorna `id` + `receipt_number`.
- [x] **AC-3:** RPC `attach_receipt_pdf(p_receipt_id, p_pdf_path)` — só professora, só se `pdf_path IS NULL`.
- [x] **AC-4:** RPC `void_insurance_receipt(p_receipt_id, p_reason)` — só professora, motivo obrigatório, só de `issued` para `void`. Registra em `audit_log` (`action = 'receipt.void'`).
- [x] **AC-5:** RLS: SELECT para professora (todos) e aluno (`student_id = auth.uid()`). **Sem** policy de INSERT/UPDATE/DELETE para `authenticated` — tudo passa pelas RPCs.
- [x] **AC-6:** Bucket privado `insurance-receipts`, caminho `{student_id}/{receipt_id}.pdf`. Storage policies: professora faz INSERT e SELECT em tudo; aluno faz SELECT só na pasta `{auth.uid()}/`. Ninguém faz UPDATE/DELETE. Só `application/pdf`, até 2 MB.
- [x] **AC-7:** Emissão registra `audit_log` (`action = 'receipt.issue'`, sem dados do snapshot no log — só ids e número).
- [ ] **AC-8:** Testes no SQL Editor: aluno não chama `issue_insurance_receipt`; aluno não vê recibo de outro; UPDATE direto é negado; numeração não repete em duas emissões simultâneas.

## Dev Notes
- Fluxo da emissão (consumido pela 3.5): `issue_insurance_receipt` → gera PDF no navegador com o número retornado → upload em `insurance-receipts/{student_id}/{id}.pdf` → `attach_receipt_pdf`. Se o upload falhar, o recibo existe sem PDF e a tela oferece "gerar PDF novamente" a partir do snapshot (o PDF é determinístico).
- O formulário tem 10 linhas de tratamento (5 × 2 colunas) e 4 de produtos — daí os limites.
- Padrão de `audit_log`: ver `20260617100000_create_audit_log.sql`.
- Soft delete de aluno (`deleted_at`) não deve apagar recibos.

## Riscos

| Risco | Prob. | Impacto | Mitigação |
|-------|-------|---------|-----------|
| Número duplicado em emissões simultâneas | Baixa | Alto | `FOR UPDATE` no contador + `UNIQUE` |
| Recibo alterado depois de emitido | Baixa | Alto | Sem policy de UPDATE; só RPC de anulação |
| Aluno baixa PDF de outro aluno | Baixa | Alto | Policy de storage por pasta + AC-8 |

## Dev Agent Record
- Migration: `supabase/migrations/20261112070000_create_insurance_receipts.sql` (BEGIN/COMMIT, idempotente; para no início se faltar `is_staff()`, `audit_log` ou o schema `storage`).
- Teste AC-8 (produção, termina em ROLLBACK): `docs/testes/3.3-recibos-teste.sql`. Reversão (só sem recibos nem PDFs): `docs/testes/3.3-recibos-reversao.sql`.
- Decisões:
  - Quem pode: `public.is_staff()` (professora ou admin, mesmo padrão das migrations de segurança), sempre com JWT (`auth.uid()` vira `issued_by`/`voided_by`). service_role e SQL sem JWT não emitem.
  - Numeração: `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` em `receipt_counters`, na mesma transação do recibo. Trava a linha como o `SELECT ... FOR UPDATE` pedido e também cobre o 1º recibo do ano (linha ainda inexistente). Rollback desfaz o número (sem buraco); sem SEQUENCE. Ano = ano de Montréal na emissão. Acima de 9999 o número cresce (`K-2026-10000`), não corta.
  - Imutabilidade além da RLS: trigger em `insurance_receipts` recusa DELETE/TRUNCATE e qualquer UPDATE que não seja anexar o PDF uma vez ou anular, para todos os papéis (inclusive service_role e SQL Editor).
  - Validação no servidor: 1–10 tratamentos `{date: "AAAA-MM-DD", amount: número}` (data válida e não futura; valor > 0, até 2 casas); 0–4 produtos `{name, price}` só em naturopathy; snapshot objeto JSON até 64 KB; aluno precisa ter `role = 'student'`. Tratamentos/produtos gravados normalizados; totais e nº de consultas calculados no servidor; `consultations_count`, `total_fees`, `total_products` NOT NULL.
  - `attach_receipt_pdf`: caminho tem de ser exatamente `{student_id}/{receipt_id}.pdf`; repetir com o mesmo caminho é aceito sem mudar nada (retentativa segura).
  - Storage: a professora só consegue enviar arquivo no caminho de um recibo existente (não dá para pôr PDF solto no bucket). Sem UPDATE/DELETE para ninguém da API.
  - `audit_log`: `receipt.issue` e `receipt.void` com `target_id = student_id` e `snapshot_data` só com `receipt_id`, `receipt_number`, `receipt_type`, `student_id`.
  - RPC de emissão devolve `{"id": uuid, "receipt_number": text}` (jsonb).
- Achado para a 3.5: os FKs sem CASCADE fazem o "apagar de vez" (`manage-student`, `hard-delete`) falhar no último passo para aluno com recibo, **depois** de já ter apagado turmas, check-ins, histórico de créditos e notificações (os deletes não são uma transação só). Antes de liberar a emissão, a `hard-delete` precisa recusar aluno com recibo antes de apagar qualquer coisa. Registrado no `docs/PENDENCIAS.md`.
