# Story 3.1 — Banco: Dados de Seguro do Aluno e Dados Profissionais da Professora

**Epic:** 3 — Recibos para Seguro Saúde (PRD-002)
**Status:** Done
**Estimativa:** M (3–5h)
**Tipo:** Database + Migration + RLS
**Esforço:** dev-critico

---

## User Story

**Como** professora,
**Quero** que o sistema guarde o número da apólice e os dados do titular de cada aluno, e os meus dados profissionais,
**Para que** os recibos de seguro sejam preenchidos automaticamente.

---

## Acceptance Criteria

- [x] **AC-1:** Tabela `student_insurance` (1:1 com aluno) com: `student_id UUID PK REFERENCES profiles(id) ON DELETE CASCADE`, `policy_number TEXT`, `city_province TEXT`, `holder_is_self BOOLEAN NOT NULL DEFAULT true`, `holder_full_name TEXT`, `holder_city_province TEXT`, `holder_employer TEXT`, `holder_occupation TEXT`, `holder_phone_work TEXT`, `holder_phone_home TEXT`, `created_at`, `updated_at` (trigger de `updated_at`).
- [x] **AC-2:** RLS em `student_insurance`: aluno faz SELECT/INSERT/UPDATE só da própria linha (`student_id = auth.uid()`); professora (`profiles.role = 'teacher'`) faz SELECT/INSERT/UPDATE de todas; DELETE bloqueado para `authenticated` (só cascade).
- [x] **AC-3:** Tabela `practitioner_credentials` (1:1 com professora): `teacher_id UUID PK REFERENCES profiles(id)`, `professional_name TEXT`, `kinesitherapy_license TEXT`, `naturopathy_license TEXT`, `signature_path TEXT` (caminho no storage), `created_at`, `updated_at`.
- [x] **AC-4:** RLS em `practitioner_credentials`: só a própria professora faz SELECT/INSERT/UPDATE (`teacher_id = auth.uid()` e role teacher). Alunos não leem.
- [x] **AC-5:** Bucket privado `practitioner-signatures` (público = false). Policies em `storage.objects`: professora lê/escreve só na pasta `{auth.uid()}/`. Limite: PNG/JPEG, até 500 KB.
- [x] **AC-6:** Nenhuma tabela ou coluna existente é alterada. Tudo com `IF NOT EXISTS`. Comentário de rollback no SQL.
- [ ] **AC-7:** Testado no SQL Editor: aluno A não lê `student_insurance` do aluno B; aluno não lê `practitioner_credentials`.

## Dev Notes

- Padrão de verificação de professora já usado: `EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'teacher')` (ver `20260717000000_create_schedule_slots.sql`).
- Por que tabela separada e não colunas em `profiles`: `profiles` é lido em muitos lugares (listas, check-in, relatórios); apólice e dados do titular são sensíveis e não devem viajar junto.
- O trigger `prevent_privilege_escalation` (em `profiles`) não é afetado.
- Telefones e cidade do titular ficam como texto livre (sem validação de formato).

## Riscos

| Risco | Prob. | Impacto | Mitigação |
|-------|-------|---------|-----------|
| Policy permissiva expõe apólice de outro aluno | Média | Alto | AC-7 com teste explícito entre dois alunos |
| Assinatura exposta publicamente | Baixa | Alto | Bucket privado; acesso só via signed URL da própria professora |

## Dev Agent Record
- Migration: `supabase/migrations/20261112000000_create_student_insurance_and_practitioner.sql`.
- Trigger de `updated_at` reusa `public.update_updated_at_column()` (de `20260201040001_create_testimonials_table.sql`); a migration só cria a função (com `SET search_path = ''`) se ela não existir, sem alterar a existente.
- Storage: além de SELECT/INSERT/UPDATE, a professora tem DELETE na própria pasta, para o botão "remover assinatura" da Story 3.2. Tabelas continuam sem DELETE para `authenticated`.
- Roteiro AC-7: `docs/testes/3.1-rls-seguro-e-credenciais.sql` (transação com ROLLBACK). Inclui um pré-requisito: o aluno não pode mudar o próprio `profiles.role`.
- **Achado fora do escopo (crítico):** `prevent_privilege_escalation()` é `SECURITY DEFINER`, então dentro dele `current_user` é o dono da função (`postgres`) e o guard nunca bloqueia. Em Postgres local, um aluno autenticado conseguiu `UPDATE profiles SET role = 'teacher'` e alterar créditos. Isso invalida todos os checks de professora, inclusive os desta story. Ver `docs/PENDENCIAS.md`.
